## 1. Token verification

- `GET /user/tokens/verify` (operationId `user-api-tokens-verify-token`) and `GET /accounts/{account_id}/tokens/verify` (`account-api-tokens-verify-token`, path param `account_id` is 32 chars). Both are described only as "Test whether a token works." Auth is bearer API token. Source: OPENAPI; https://developers.cloudflare.com/api/resources/user/subresources/tokens/methods/verify/ and https://developers.cloudflare.com/api/resources/accounts/subresources/tokens/methods/verify/
- Response `result`: `id` (string, max 32, required), `status` (required; enum `active`, `disabled`, `expired`), `not_before` (date-time, optional), `expires_on` (date-time, optional). Envelope: `success`, `errors[]`, `messages[]`. Source: OPENAPI, both operations identical. That the two timestamps are omitted for tokens with no TTL is an inference, UNVERIFIED.
- Docs example for the user endpoint shows `result` with only `id` and `status`, plus `messages: [{code: 10000, message: "This API Token is valid and active", type: null}]`. Source: https://developers.cloudflare.com/fundamentals/api/get-started/create-token/ (fixture `fixtures-token-verify-docs.json`). An example with all four result fields: https://developers.cloudflare.com/fundamentals/api/troubleshooting/
- Failure shape per OPENAPI 4XX: `success: false`, `result: null`.
- Telling account-owned from user tokens by format: new tokens are `cfut_` + 40 chars + checksum (user) and `cfat_` + 40 chars + checksum (account). Tokens created before the 2026 prefix scheme are unprefixed 40-char alphanumeric strings for both types, so they cannot be told apart by format. Source: https://developers.cloudflare.com/fundamentals/api/get-started/token-formats/
- The verify response has no field naming the token's owner type. Source: OPENAPI (result properties above).
- Which verify endpoint accepts which token type: **UNVERIFIED**. No fetched page says the user endpoint rejects account tokens or the reverse. Suggested approach: if the token starts with `cfat_` call the account endpoint; otherwise try the account endpoint with the configured account ID, and fall back to the user endpoint. Test against live tokens before relying on it.
- Account-owned tokens are supported for "Tunnels" and "Account Analytics" per the compatibility matrix. Source: https://developers.cloudflare.com/fundamentals/api/get-started/account-owned-tokens/

## 2. Cloudflare Tunnel (cfd_tunnel)

### List tunnels
- `GET /accounts/{account_id}/cfd_tunnel` (`cloudflare-tunnel-list-cloudflare-tunnels`). Source: OPENAPI; https://developers.cloudflare.com/api/resources/zero_trust/subresources/tunnels/subresources/cloudflared/methods/list/
- Query params: `name`, `is_deleted` (bool; true = only deleted, false = exclude deleted, empty = all), `existed_at` (URL-encoded time), `uuid`, `was_active_at`, `was_inactive_at`, `include_prefix`, `exclude_prefix`, `status` (enum `inactive`, `degraded`, `healthy`, `down`), `per_page` (min 1, **max 1000**, no default stated), `page` (min 1, default 1). Source: OPENAPI.
- `result_info` fields: `page`, `per_page`, `count`, `total_count`. There is **no `total_pages` and no cursor** in the tunnel schema (the zones list does have `total_pages`). Compute pages as `ceil(total_count / per_page)` or stop when `count < per_page`. Source: OPENAPI. The schema describes `total_count` as "Total results available without any search parameters", so it may not reflect filtered counts (schema wording; actual behavior UNVERIFIED). Prefer the `count < per_page` stop condition.
- Tunnel object fields (all optional in the schema): `id` (uuid), `account_tag`, `name`, `status`, `created_at`, `deleted_at` (null if not deleted), `conns_active_at` (null if inactive), `conns_inactive_at` (null if active), `config_src` (`local` | `cloudflare`, default `local`), `remote_config` (bool), `tun_type` (enum `cfd_tunnel`, `warp_connector`, the client type, `magic`, `ip_sec`, `gre`, `cni`), `metadata` (object), `connections[]`. Source: OPENAPI.
- Status semantics: `inactive` = never run; `degraded` = active and able to serve traffic but unhealthy; `healthy` = active and able to serve; `down` = no connections to the edge. Source: OPENAPI `tunnel_status` schema.
- `connections[]` on the tunnel object (schema `tunnel_schemas-connection`): `id`, `uuid`, `client_id`, `client_version`, `colo_name`, `is_pending_reconnect` (deprecated; "will now always report false"), `opened_at`, `origin_ip` ("public IP address of the host running cloudflared"). Source: OPENAPI.
- Whether the list endpoint actually populates `connections[]` (versus only the single-tunnel GET): **UNVERIFIED**. The list schema declares the field; a live call is needed.
- Get one: `GET /accounts/{account_id}/cfd_tunnel/{tunnel_id}` returns the same object. Source: OPENAPI.

### Connections
- `GET /accounts/{account_id}/cfd_tunnel/{tunnel_id}/connections` (`cloudflare-tunnel-list-cloudflare-tunnel-connections`). Source: OPENAPI; https://developers.cloudflare.com/api/resources/zero_trust/subresources/tunnels/subresources/cloudflared/subresources/connections/methods/get/
- Description: "Lists the connections for a Cloudflare Tunnel, including connector IDs, cloudflared versions, and Cloudflare locations." No query params. The response has `result_info` (`page`, `per_page`, `count`, `total_count`).
- `result[]` is a list of connector clients with: `id` (uuid, the connector/client ID), `arch` (e.g. `linux_amd64`), `version` (cloudflared version), `run_at`, `features[]` (strings), `config_version` (integer), `conns[]`. Each `conns[]` item has the same fields as the tunnel `connections[]` items: `colo_name`, `id`, `uuid`, `client_id`, `client_version`, `is_pending_reconnect`, `opened_at`, `origin_ip`. Source: OPENAPI. This matches your field list, with `client_id`, `client_version` and `uuid` also present on each conn and `config_version` on the client.
- `GET /accounts/{account_id}/cfd_tunnel/{tunnel_id}/connectors/{connector_id}` exists (`cloudflare-tunnel-get-cloudflare-tunnel-connector`) and returns one such client object (no `result_info`). Source: OPENAPI.
- The generic `GET /accounts/{account_id}/tunnels` exists (`cloudflare-tunnel-list-all-tunnels`, "Lists and filters all types of Tunnels"). Same filters as cfd_tunnel plus `tun_types` (array, comma-separated); `per_page` max 1000. Its `result` items are untyped in the schema, so the per-type shape is **UNVERIFIED**. Source: OPENAPI.
- Related but out of scope: `/accounts/{account_id}/warp_connector/{tunnel_id}/connectors/{connector_id}` and `/accounts/{account_id}/magic/connectors/...` exist. Source: OPENAPI.

## 3. Token permissions

- Tunnel list, get, connections, and connector get: at least one of `Cloudflare One Connectors Read`, `Cloudflare One Connector: cloudflared Read`, `Cloudflare Tunnel Read` (the Write variants also satisfy). All are Account-scope permissions. Source: https://developers.cloudflare.com/api/resources/zero_trust/subresources/tunnels/subresources/cloudflared/methods/list/ ("Accepted Permissions (at least one required)"); OPENAPI `x-api-token-group`; scope: https://developers.cloudflare.com/fundamentals/api/reference/permissions/ (Account permissions, scope `com.cloudflare.api.account`). `Cloudflare Tunnel Read` is described as "Grants access to view Cloudflare Tunnels."
- "Argo Tunnel Read" does not appear on the permissions page or in the OPENAPI token groups for these endpoints. Treat as an obsolete name, **UNVERIFIED**.
- `GET /zones` (list zones): the accepted permission is listed as `Zone Zone Read` in the API reference and OPENAPI; the permissions page lists `Zone Read` ("Grants read access to zone management", Zone scope `com.cloudflare.api.account.zone`). Sources: https://developers.cloudflare.com/api/resources/zones/methods/list/ ; https://developers.cloudflare.com/fundamentals/api/reference/permissions/ . The label mismatch is in the sources themselves.
- `GET /zones` query: `account.id`, `account.name`, `name`, `status` (`initializing`, `pending`, `active`, `moved`), `type`, `page` (default 1), `per_page` (default 20, **min 5, max 50**), `order`, `direction`, `match`. `result_info` here includes `total_pages`. Zone object includes `id`, `name`, `account{id,name}`, `paused`, `plan`. Source: OPENAPI. Listing zones across more than 500 accounts is not allowed.
- Analytics: the GraphQL docs configure the token as Account > Account Analytics > Read with zone resources set. The permissions page lists `Account Analytics Read` (Account scope) and `Analytics Read` (Zone scope). Sources: https://developers.cloudflare.com/analytics/graphql-api/getting-started/authentication/api-token-auth/ ; https://developers.cloudflare.com/fundamentals/api/reference/permissions/ . The name "Zone Analytics Read" is **UNVERIFIED** (the page uses "Analytics Read" under Zone permissions). The GraphQL error page says the token needs "Analytics: Read" for the relevant resources: https://developers.cloudflare.com/analytics/graphql-api/errors/
- Which of the two analytics permissions is strictly required for a zone-scoped `httpRequestsAdaptiveGroups` query: **UNVERIFIED**. Grant `Analytics Read` on the zones plus `Account Analytics Read`, then test with narrower sets.

## 4. REST rate limits and errors

- Limits table: Client API per user/account token 1200 per 5 minutes; per IP 200 per second; GraphQL "varies by query cost, max 320/5 min"; user API tokens per user 50; account API tokens per account 500. Source: https://developers.cloudflare.com/fundamentals/api/reference/limits/
- The note on the same page: the global limit is 1,200 requests per five minutes per user, cumulative across dashboard, API key and API token. Exceeding it blocks all calls for the next five minutes with `HTTP 429 - Too Many Requests`. Same source.
- Conflict: that page says GraphQL max 320 per 5 min, while the GraphQL limits page says 300 per 5 minutes (Q5). Plan on 300.
- Headers on REST responses: `Ratelimit` (e.g. `"default";r=50;t=30`: limit name, remaining `r`, seconds until window reset `t`), `Ratelimit-Policy` (e.g. `"burst";q=100;w=60`: name, quota `q`, window `w`), `retry-after` (seconds, rounded up; only present once the limit is exceeded). Source: https://developers.cloudflare.com/fundamentals/api/reference/limits/ (section "Rate limiting headers").
- HTTP 429 REST response body: **UNVERIFIED**. No fetched page documents it. Key off the status and `retry-after` rather than parsing the body.
- Standard envelope: `success` (bool), `errors[]` (`code` integer >= 1000, `message`, optional `documentation_url`, optional `source.pointer`), `messages[]` (same shape), `result`, and `result_info` for lists. The failure variant requires `success: false` and `result: null`. Source: OPENAPI (`tunnel_api-response-common-failure`, verify-token schemas). Schema example: `{code: 7003, message: "No route for the URI"}` (`fixtures-error-envelope.json`).
- Error codes: `10000` with message "Authentication error" is the example for auth failures throughout OPENAPI (232 occurrences of `10000`); `10000` also appears as an informational message ("This API Token is valid and active") on a successful verify (create-token page above). Codes `1000` and `9109` were not found in OPENAPI or any fetched docs page: **UNVERIFIED**. Do not hard-code codes other than `10000` and `7003`; treat HTTP 401/403 plus `success: false` as the auth-failure signal.
- Auth header: `Authorization: Bearer <token>` (OPENAPI security scheme `api_token`, http bearer). The troubleshooting page warns against using key syntax with a token: https://developers.cloudflare.com/fundamentals/api/troubleshooting/

## 5. GraphQL Analytics API

- Endpoint: `https://api.cloudflare.com/client/v4/graphql`, single endpoint, `POST` with a JSON payload. Source: https://developers.cloudflare.com/analytics/graphql-api/
- Auth: API token (preferred) or Global API key; the token needs analytics read on the account and zones (see Q3). Source: https://developers.cloudflare.com/analytics/graphql-api/getting-started/authentication/ and `.../authentication/api-token-auth/`
- Limits, three layers. Source: https://developers.cloudflare.com/analytics/graphql-api/limits/
  - Global: a zone-scoped query includes up to 10 zones; an account-scoped query includes 1 account; the number of queries per request equals scopes multiplied by nodes.
  - User: default 300 GraphQL queries per 5-minute window (at least 1 query per second sustained, or a burst of 300).
  - Node: per-dataset limits on lookback, max time range, field count, and rows returned, tied to `zoneTag`/`accountTag` and plan.
  - Optional account-based rate limiting (limits per account and zone instead of per token): https://developers.cloudflare.com/analytics/graphql-api/account-based-rate-limiting/
- Query cost: the REST limits page says GraphQL "varies by query cost", but no formula or cost header was found: **UNVERIFIED**.
- Errors: HTTP 200 may still carry an `errors` array (fields `message`, `path`, `extensions.timestamp`). Documented messages: `rate limiter budget depleted, try again after 5 minutes` (429), `in combination, your request queries too many nodes, zones and accounts` (429), `query consumed excessive resources...` (429), `cannot request data older than...` (400), `Unauthorized` (401), `not authorized for that account` (403), `unable to execute query, please try again later` (503). Account-based limiting returns `extensions.code: "budget"`. Sources: https://developers.cloudflare.com/analytics/graphql-api/errors/ and `.../account-based-rate-limiting/` (fixture `fixtures-graphql-rate-limit.json`).
- Discovery via the `settings` node, available under `viewer.zones(filter:{zoneTag})` and `viewer.accounts(filter:{accountTag})`. Fields per dataset: `enabled`, `availableFields`, `maxPageSize`, `maxNumberOfFields`, `notOlderThan` (seconds back), `maxDuration` (seconds per query). Documented sample for `firewallEventsAdaptive`: `enabled true, maxDuration 259200, maxNumberOfFields 30, maxPageSize 10000, notOlderThan 2678400` (fixture `fixtures-graphql-settings.json`). Source: https://developers.cloudflare.com/analytics/graphql-api/features/discovery/settings/
- Settings key naming: docs samples query `settings { httpRequestsAdaptive { ... } }` (the raw dataset name, without `Groups`) in the firewall-events tutorial, https://developers.cloudflare.com/analytics/graphql-api/tutorials/querying-firewall-events/ . Whether `settings.httpRequestsAdaptiveGroups` exists: **UNVERIFIED**. Use introspection or the raw name.
- Datasets:
  - `httpRequestsAdaptiveGroups` is the documented canonical HTTP source, and "all plans" get "the essential datasets (like `httpRequestsAdaptiveGroups`, `firewallEventsAdaptive`)". Adaptive datasets retain at least 31 days on every plan. Source: https://developers.cloudflare.com/analytics/graphql-api/features/discovery/settings/ and `.../limits/`
  - `firewallEventsAdaptive` (raw) and `firewallEventsAdaptiveGroups` (grouped; used in the data-sets page example with `count` and `dimensions{datetimeHour}`). Security Events retention is up to 31 days on Free, Pro, Business and Enterprise; max query window 30 days (Free, Pro, Business) or 31 days (Enterprise). Source: https://developers.cloudflare.com/waf/analytics/security-events/ (Availability table); https://developers.cloudflare.com/analytics/graphql-api/features/data-sets/
  - `httpRequests1mGroups` and `httpRequests1hGroups` appear in docs examples (filter `datetime_geq`/`datetime_lt`; dimensions `datetimeMinute`/`datetimeFiveMinutes`; `sum{bytes, cachedBytes, requests, cachedRequests, threats, pageViews}`; `uniq{uniques}`). Source: https://developers.cloudflare.com/analytics/graphql-api/features/data-sets/ and `.../migration-guides/zone-analytics/`. Per-plan availability and retention for these aggregated nodes: **UNVERIFIED** (the limits page says only that they "keep their own per-plan limits"). Query `settings` per zone to find out.
  - Deprecated per docs: `httpRequests1mByColoGroups` and `httpRequests1dByColoGroups` (replace with `httpRequestsAdaptiveGroups`). Source: https://developers.cloudflare.com/analytics/graphql-api/migration-guides/ . The docs do not mark `httpRequests1mGroups` or `1hGroups` deprecated; introspection reports deprecation status per node (https://developers.cloudflare.com/analytics/graphql-api/features/discovery/introspection/).
  - Tunnel analytics: no GraphQL dataset for cloudflared tunnels was found in the analytics docs. Tunnel-named datasets that do exist belong to Magic Transit/WAN IPsec/GRE (`magicTransitTunnelHealthChecksAdaptiveGroups`, `conduitEdgeTunnelHealthChecks`, tunnel bandwidth), a different product. Source: https://developers.cloudflare.com/analytics/graphql-api/ tutorials index (via https://developers.cloudflare.com/analytics/llms.txt). A text search of the docs bundle https://developers.cloudflare.com/llms-full.txt (68 MB) found no cloudflared GraphQL node. Conclusion: for cloudflared tunnels use the REST API (Q2) and local metrics (Q6).
- `httpRequestsAdaptiveGroups` shape confirmed by docs examples:
  - Filter: `filter: { datetime_geq: $start, datetime_lt: $end, requestSource: "eyeball" }`; also `datetime_gt`, `clientRequestHTTPHost`, `clientCountryName`, `coloCode`. Variable types used in docs: `$zoneTag: string`, `$start: Time`. `limit` is given in every example (values 1 to 10000; ceiling is `maxPageSize`); `orderBy` examples: `[count_DESC]`, `[sum_edgeResponseBytes_DESC]`, `[datetimeHour_ASC]`. Sources: https://developers.cloudflare.com/analytics/graphql-api/migration-guides/graphql-api-analytics/ ; https://developers.cloudflare.com/analytics/graphql-api/tutorials/end-customer-analytics/
  - Measures: `count` (requests), `sum { edgeResponseBytes visits }`, `avg { sampleInterval }`. Same sources. `visits` counts page views whose referer differs from the hostname or is direct.
  - Dimensions seen in docs: `datetimeHour`, `coloCode`, `clientRequestPath`. Same sources.
  - `datetimeMinute` as a dimension of `httpRequestsAdaptiveGroups`: **UNVERIFIED** (docs show it for `httpRequests1mGroups`).
  - `cacheStatus` as a dimension of `httpRequestsAdaptiveGroups`: **UNVERIFIED**. Not found in the GraphQL docs; `cacheStatus` in the docs bundle refers to AI Gateway, Hyperdrive and log fields only. Confirm by introspection with a real token (https://developers.cloudflare.com/analytics/graphql-api/getting-started/explore-graphql-schema/).
  - `edgeResponseStatus` appears only inside `httpRequests1mGroups.sum.responseStatusMap` in the Zone Analytics migration page. As a dimension of `httpRequestsAdaptiveGroups`: **UNVERIFIED**.
  - Adaptive datasets are sampled (adaptive bit rate); `sampleInterval` describes the sampling. Source: https://developers.cloudflare.com/analytics/graphql-api/sampling/
- Data latency for adaptive HTTP datasets: **UNVERIFIED**. No fetched page states a delay figure. Retention per plan (Free/Pro/Business/Enterprise) is documented only as "at least 31 days on every plan" for adaptive datasets plus the Security Events table above.
- The GraphQL API is not a billing measure (it includes traffic that billing excludes, such as DDoS). Source: https://developers.cloudflare.com/analytics/graphql-api/

## 6. cloudflared local metrics server

- Default address, non-containerized: `127.0.0.1:<PORT>/metrics` where PORT is the first free port from `20241` to `20245`; if all are busy, a random port. Containerized (Docker, Kubernetes): `0.0.0.0:<PORT>/metrics`. The chosen address is logged at startup ("Starting metrics server on 127.0.0.1:20241/metrics"). Override with `--metrics <IP:PORT>` or env `TUNNEL_METRICS`. Source: https://developers.cloudflare.com/cloudflare-one/networks/connectors/cloudflare-tunnel/monitor-tunnels/metrics/ and https://developers.cloudflare.com/cloudflare-one/networks/connectors/cloudflare-tunnel/configure-tunnels/run-parameters/ . The source code confirms the `localhost:20241..20245` and `0.0.0.0:20241..20245` lists: https://raw.githubusercontent.com/cloudflare/cloudflared/master/metrics/metrics.go
- The release in which the 20241-20245 range began: **UNVERIFIED**. A code comment says the ports were selected in 2024; no release number was found. Port `2000` appears in guides only as an explicit `--metrics 0.0.0.0:2000` argument (https://developers.cloudflare.com/tunnel/guides/kubernetes/), not as a default.
- Metrics documented (name, type, labels), all at the metrics page above:
  - `cloudflared_tunnel_ha_connections` GAUGE, number of active HA connections.
  - `cloudflared_tunnel_total_requests` COUNTER, requests proxied through all tunnels.
  - `cloudflared_tunnel_request_errors` COUNTER, errors proxying to origin.
  - `cloudflared_tunnel_concurrent_requests_per_tunnel` GAUGE.
  - `cloudflared_tunnel_active_streams` GAUGE.
  - `cloudflared_tunnel_server_locations` GAUGE, labels `connection_id`, `edge_location` (1 = current, 0 = previous).
  - `cloudflared_tunnel_timer_retries` GAUGE, unacknowledged heartbeats.
  - `cloudflared_tunnel_tunnel_authenticate_success` COUNTER; `cloudflared_tunnel_tunnel_register_success` COUNTER (label `rpcName`).
  - `cloudflared_tcp_active_sessions` GAUGE, `cloudflared_tcp_total_sessions` COUNTER, `cloudflared_udp_active_sessions` GAUGE, `cloudflared_udp_total_sessions` COUNTER.
  - `cloudflared_orchestration_config_version` GAUGE; `cloudflared_config_local_config_pushes` and `..._errors` COUNTER.
  - `quic_client_latest_rtt`, `quic_client_min_rtt`, `quic_client_smoothed_rtt` GAUGE (label `conn_index`); `quic_client_total_connections`, `quic_client_closed_connections`, `quic_client_lost_packets` (labels `conn_index`, `reason`), `quic_client_packet_too_big_dropped` COUNTER.
  - `build_info` GAUGE (labels `goversion`, `revision`, `type`, `version`), plus standard `go_*` and `promhttp_*` metrics.
- `/ready`: the Kubernetes guide comment states "Cloudflared has a /ready endpoint which returns 200 if and only if it has an active connection to Cloudflare's network." Source: https://developers.cloudflare.com/tunnel/guides/kubernetes/ . The metrics docs page does not mention `/ready`.
  - Source-level detail (cloudflared repository, not a docs page; read, not executed): `/ready` returns HTTP 200 when at least one connection is active, otherwise 503, with JSON body `{"status": <http code>, "readyConnections": <uint>, "connectorId": "<uuid>"}`. Source: https://raw.githubusercontent.com/cloudflare/cloudflared/master/metrics/readiness.go . The same router serves `/healthcheck` (returns `OK`), `/metrics`, `/quicktunnel`, and `/config` when an orchestrator is present (https://raw.githubusercontent.com/cloudflare/cloudflared/master/metrics/metrics.go). These are from master; availability in older releases is **UNVERIFIED**.

## Discrepancies and open items

1. GraphQL rate limit: 320 per 5 min (https://developers.cloudflare.com/fundamentals/api/reference/limits/) versus 300 per 5 min (https://developers.cloudflare.com/analytics/graphql-api/limits/). Use 300.
2. The Zone Read permission label differs between the API reference (`Zone Zone Read`) and the permissions page (`Zone Read`).
3. Not found in any fetched source: REST 429 body, error codes `1000`/`9109`, GraphQL query-cost formula, adaptive-dataset latency, `cacheStatus`/`datetimeMinute`/`edgeResponseStatus` on `httpRequestsAdaptiveGroups`, Free-plan availability of `httpRequests1mGroups`/`1hGroups`, and which verify endpoint pairs with which token type. Resolve with one authenticated GraphQL introspection call and one live verify call before coding against them.
4. The Cloudflare MCP server failed to connect during this research, so no authenticated calls were made. Everything above comes from public docs, the public OpenAPI schema, and cloudflared source, not live responses.
